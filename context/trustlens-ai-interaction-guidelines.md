# TrustLens AI Interaction Guidelines

These guidelines define how AI coding assistants should work on the
TrustLens codebase. They complement the TrustLens Coding Standards and
project specification.

## Communication

-   Be concise and direct.
-   Explain non-obvious technical and security decisions briefly.
-   Ask before large refactors, architectural changes, dependency
    replacements, or destructive operations.
-   Do not add features that are not in the project specification.
-   Never delete files, database collections, migrations/data, branches,
    or significant functionality without explicit permission.
-   When requirements are ambiguous and the ambiguity could materially
    change implementation, ask before proceeding.
-   For small implementation details that follow established project
    patterns, proceed without unnecessary clarification.
-   Clearly state when a proposed change affects TrustLens security
    boundaries, scan behavior, risk scoring, authentication, or
    persisted data.

## Source of Truth

Before implementing a feature, follow this priority:

1.  Current feature requirements in `context/current-feature.md`.
2.  TrustLens project specification/architecture.
3.  TrustLens Coding Standards.
4.  Existing codebase patterns.
5.  This AI Interaction Guidelines document.

If two sources conflict, do not silently choose one when the conflict
affects architecture, security, or feature behavior. Explain the
conflict and ask for clarification.

## Workflow

Use this workflow for each feature or fix:

1.  **Document** --- Define the feature/fix, scope, acceptance criteria,
    and relevant security considerations in
    `context/current-feature.md`.
2.  **Branch** --- Create a dedicated branch from the latest intended
    base branch.
3.  **Implement** --- Make the smallest complete change that satisfies
    `context/current-feature.md`.
4.  **Validate** --- Run relevant type checking, linting, tests, and
    `npm run build`. For UI work, verify the affected flow in the
    browser.
5.  **Security Check** --- For security-sensitive work, verify
    authentication, authorization, input validation, secret handling,
    SSRF/network boundaries, and data exposure as applicable.
6.  **Iterate** --- Fix issues discovered during validation without
    expanding scope unnecessarily.
7.  **Review** --- Review the diff for unrelated changes, dead code,
    security problems, and accidental secret/data exposure.
8.  **Commit** --- Only after validation passes and the user explicitly
    approves the commit.
9.  **Merge** --- Merge only with user approval and according to the
    project's Git workflow.
10. **Delete Branch** --- Ask before deleting the merged branch.
11. **Complete** --- Mark the feature as completed in
    `context/current-feature.md` and add the appropriate history entry.

Do **not** commit, merge, delete branches, or perform other destructive
Git operations without permission.

If `npm run build`, type checking, linting, or required tests fail
because of the change, fix the failures before requesting permission to
commit. If a failure is clearly pre-existing or unrelated, report it
rather than silently changing unrelated code.

## Branching

Create a dedicated branch for each feature or fix.

Preferred naming:

``` text
feature/<short-description>
fix/<short-description>
refactor/<short-description>
chore/<short-description>
```

Examples:

``` text
feature/new-scan
feature/risk-report
fix/scan-url-validation
fix/auth-redirect
```

-   Use lowercase kebab-case descriptions.
-   Do not mix unrelated features/fixes in one branch.
-   Ask before deleting a branch after merge.

## Commits

-   Never commit automatically.
-   Ask for explicit permission before committing.
-   Use Conventional Commits.

Examples:

``` text
feat: add website scan submission
fix: block private IP scan targets
refactor: extract risk scoring service
chore: configure scan worker
```

-   Keep commits focused.
-   Do not include unrelated formatting/refactors.
-   Do not add AI attribution such as `Generated With Claude`,
    `Generated by ChatGPT`, or similar text to commit messages unless
    explicitly requested.
-   Never commit secrets, `.env` credentials, tokens, private keys, or
    sensitive scan artifacts.

## TrustLens Security Boundaries

TrustLens investigates potentially malicious websites, so
security-related code requires additional care.

AI coding assistants must:

-   Treat every user-submitted URL and scanned website as untrusted.
-   Never bypass the centralized URL/SSRF validation layer to make a
    scan work.
-   Never navigate to a user-submitted suspicious URL directly from the
    user's browser.
-   Keep Playwright/Chromium scanning inside the designated isolated
    scanner service.
-   Never weaken private-IP, loopback, link-local, reserved-address,
    redirect, or DNS-rebinding protections without explicit approval.
-   Never expose MongoDB, Redis, internal services, cloud metadata
    endpoints, or application secrets to the scanner unnecessarily.
-   Never place secrets in client-side TanStack Start code.
-   Never log passwords, session tokens, API keys, authorization
    headers, cookies, or sensitive URL query values.
-   Treat scanned page content as untrusted data when sending evidence
    to an AI model.
-   Never allow AI-generated text to override deterministic security
    evidence silently.
-   Never change risk weights, verdict thresholds, or confidence rules
    as an incidental part of another feature.

If a requested implementation would weaken one of these boundaries, stop
and explain the concern before making the change.

## TanStack Start

TrustLens uses **TanStack Start**, not Next.js.

When generating or modifying application code:

-   Follow TanStack Start and TanStack Router conventions already
    present in the project.
-   Do not introduce Next.js APIs, directories, Server Actions,
    `use server`, `next/*` imports, or Next.js-specific patterns.
-   Keep server-only operations in the appropriate TanStack Start server
    functions/server modules.
-   Never move secrets or privileged operations into client components
    to work around a server/client issue.
-   Validate server-function and route inputs according to the TrustLens
    Coding Standards.

## Dependency Changes

-   Prefer existing dependencies and project patterns.
-   Do not install a new package merely to avoid implementing a small
    utility.
-   Ask before adding a major dependency, replacing an existing library,
    or introducing a new infrastructure service.
-   Small, clearly required dependencies may be proposed, but explain
    why the existing stack cannot reasonably handle the requirement.
-   Do not replace Better Auth, Mongoose, Redis/BullMQ, Playwright, Zod,
    or other architectural choices without explicit approval.
-   Check package compatibility with the existing runtime and TanStack
    Start setup before adoption.

## Database and Persistent Data

-   Use the existing MongoDB/Mongoose architecture.
-   Do not introduce Prisma or another ORM.
-   Do not rename/delete collections, fields, indexes, or stored data
    casually.
-   Schema changes must consider backward compatibility and existing
    records.
-   Never run destructive database operations without explicit
    permission.
-   Do not store large screenshots or scan artifacts in MongoDB when the
    architecture expects object storage.

## Risk Engine and AI

The TrustLens risk engine and AI explanation layer have separate
responsibilities.

-   Deterministic code owns structured findings, risk score, confidence,
    and verdict rules.
-   AI is primarily responsible for explaining and correlating supplied
    evidence.
-   Do not invent evidence that was not produced by the scan pipeline.
-   Do not allow an LLM response alone to mark a website safe or
    malicious.
-   Validate structured AI responses before storing or rendering them.
-   Changes to scoring rules require focused tests and explicit review.

## Testing and Validation

Run the checks relevant to the changed area.

Typical validation should include:

``` bash
npm run build
```

and the project's configured type-checking, linting, and test commands.

Additionally:

-   Use unit tests for deterministic security/risk logic.
-   Test authorization for protected resources.
-   Test Zod validation at external boundaries.
-   Test security-sensitive URL handling against controlled inputs.
-   Use browser/E2E validation for important user flows.
-   Do not test the scanner against arbitrary live malicious websites.
-   Do not weaken tests simply to make a failing implementation pass.

When reporting completion, state which checks were actually run and
whether they passed. Never claim a test or browser check was performed
if it was not.

## When Stuck

If an issue remains unresolved after 2--3 well-reasoned attempts:

1.  Stop making speculative changes.
2.  Summarize what was attempted.
3.  Explain the observed error/behavior.
4.  Identify the most likely causes.
5.  Ask for clarification or propose the smallest next diagnostic step.

Do not repeatedly install packages, change configuration, weaken typing,
disable security controls, or suppress errors until the problem
disappears.

## Code Changes

-   Make minimal changes required to accomplish the documented task.
-   Do not refactor unrelated code unless explicitly requested.
-   Do not add speculative or "nice to have" features.
-   Preserve existing project patterns unless they conflict with the
    TrustLens Coding Standards.
-   Avoid broad formatting changes that make the functional diff
    difficult to review.
-   Do not silence TypeScript/ESLint errors with unsafe casts or blanket
    ignore directives without explaining why.
-   Do not leave commented-out implementations or temporary debugging
    code.
-   Prefer fixing the root cause over suppressing an error.

## Code Review

Review AI-generated code periodically and before important merges.

Pay particular attention to:

-   **Security** --- authentication, authorization, input validation,
    SSRF, DNS/IP validation, secrets, prompt injection, artifact access.
-   **Risk integrity** --- evidence provenance, scoring logic,
    confidence, verdict thresholds.
-   **Performance** --- unnecessary React re-renders, duplicate provider
    calls, missing cache opportunities, inefficient MongoDB queries,
    missing indexes.
-   **Reliability** --- BullMQ retries, idempotency, timeouts, partial
    scan failures, provider outages.
-   **Logic** --- edge cases, null states, redirect behavior, incomplete
    evidence.
-   **Privacy** --- sensitive URLs, screenshots, logs, third-party
    provider submissions, retention.
-   **Patterns** --- consistency with TanStack Start, Mongoose, Zod,
    Better Auth, and existing project architecture.
-   **UX** --- loading, empty, error, queued, partial, and completed
    scan states.
-   **Accessibility** --- keyboard behavior, labels, focus states, and
    risk indicators that do not depend on color alone.

## Completion Report

After implementing a feature/fix, provide a concise summary containing:

-   What changed.
-   Important files changed.
-   Security implications, if any.
-   Tests/checks performed and their results.
-   Any known limitations or follow-up work.

Do not commit until the user approves.
